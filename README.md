# 📋 事务所出报告批量排版工具

> 🖥️ 面向事务所专用场景、尽量契合 `minimax-docx` 处理思路的 DOCX 批量排版桌面工具
>
> 🎨 Win11 风格深色主题界面 | 📄 基于 OpenXML 直接操作文档 | ⚡ 批量处理无需打开 Word

---

## 🌟 功能概览

- 📁 **批量处理**：选择单个文件或整个文件夹，支持递归子文件夹
- 🔍 **统一文档上下文**：先集中推导纯封面、封面、场景名、运行来源，再驱动后续链路
- 🧭 **统一规则来源**：封面规则、页边距规则、落款边界、字体字号等由统一 profile 提供
- 🔍 **自动识别文档结构**：封面页、正文标题区、文号区、抬头行、落款区全部自动识别
- 📝 **段落排版**：标题层级识别（一级/二级/三级）、正文首行缩进、行距统一
- 📊 **表格排版**：财务表格自动对齐；普通数值统一为千分位、两位小数，编号、代码、年份、数量等业务列保持原样
- 📑 **页眉页脚**：统一页眉样式、自动插入居中页码
- ✍️ **落款区排版**：精准定位落款段落集合，独立排版不受正文影响
- 📜 **纯封面文档**：自动识别（全文不足200字）并仅处理页边距
- 🚦 **统一门禁链**：主程序执行结构校验、业务校验和按需场景校验；快照导出与差异审计由验证工具独立运行

## 🚀 如何运行

### ✅ 最简单的方式（推荐）

在项目目录下找到 `run.py`，在 Trae 编辑器中打开它，点击右上角的 **▶ 三角形按钮** 即可启动。

### 🛠️ 使用步骤

1. 📂 点击 **浏览文件** 选择单个 `.docx` 文件，或点击 **浏览文件夹** 选择包含多个文档的目录
2. ✅ 勾选 **包含子文件夹** 可递归处理子目录中的文档（可选）
3. ▶️ 点击 **开始处理**，等待进度条完成
4. 💾 处理后的文件以 `_已排版` 后缀保存在原目录中；批量模式会跳过正式输出件、`_排版失败_时间戳.docx` 失败件和遗留临时件，避免重复套格式

## ⚙️ 排版流水线——处理顺序

整个排版过程像一条流水线，按固定顺序依次处理：

> 📥 **输入文件** → 复制到原目录下的临时文件（不修改原文件）
>
> 👇
>
> 🧠 **统一文档分类与上下文推导**
>
> 👇
>
> 情况一：📄 **纯封面文档**（按统一规则 profile 的可见有效文本阈值判断）→ 仅处理页边距，跳过所有其他排版
>
> 情况二：📋 **正式文档** → 按以下顺序处理：
>
> 1️⃣ **封面检测** → 扫描前60个元素，寻找包含"会计师事务所+地址+电话+传真"的表格，判断文档是否有封面
>
> 2️⃣ **页眉页脚处理** → 设置页面尺寸和边距、清理封面区域的页眉页脚、统一正文页眉样式、插入页码
>
> 3️⃣ **落款区预扫描** → 按事务所模板边界定位：先找"四川华信(集团)会计师事务所"，再找"中国·成都"，再找日期尾行；只有边界顺序正确且区间内至少有两行"中国注册会计师"时，才把整段标记为落款区
>
> 4️⃣ **正文段落排版** → 处理所有正文段落，但会跳过表格内的段落和已标记的落款区段落
>
> 5️⃣ **表格排版** → 处理所有财务表格的对齐、边框、数值格式化
>
> 6️⃣ **落款区排版** → 对预扫描圈出的落款区段落进行独立排版
>
> 👇
>
> ✅ **统一门禁** → 结构校验 + 业务校验 + 排版前后复杂结构对比；验证任务可按请求增加场景校验。快照导出与差异审计仅由 `Tools/DocxValidation` 独立执行，不属于 GUI 主流程
>
> 👇
>
> 🔁 **落盘后复核** → 关闭并重新打开临时文件，确认最终文件仍可正常读取
>
> 👇
>
> 📤 **正式输出文件** → 全部通过后才移动为 `_已排版.docx`；失败时保留为 `_排版失败_时间戳.docx` 供排查

> 💡 **核心设计原则**：先铺大底色（正文排版），再精雕细琢（表格、落款）。各服务之间通过"黑名单"机制精准避障，互不干扰——正文排版不会碰到表格里的段落，也不会碰到落款区的段落。

## 🚦 当前门禁链

- **源文档 Schema 合规修复**：排版前先清理旧版 Word 兼容格式的 schema 违规（如 `evenAndOddHeaders` 误入 `SectionProperties`、`w:style` 子元素顺序错乱），修复后再排版，不再依赖门禁放行绕过
- **基础结构校验**：`OpenXmlValidator` 报出的 schema 兼容性差异仅记警告、不阻断；正文有效可见内容、分节引用完整性和最终文件能否重新打开仍属于阻断项
- **业务规则校验**：标题、正文编号、表格数值规则、页边距、落款区核心口径
- **场景校验**：矩阵和真实样本通过统一场景服务断言，不再让 CLI 和 GUI 各自漂
- **快照导出**：可导出正文可见字数、标题、分节、页边距、页眉页脚引用、表格详情、落款命中数、复杂结构统计
- **差异审计**：`Tools/DocxValidation` 可独立对比两份 DOCX 的结构快照，并按标题、正文、表格、分节、落款、复杂结构汇总差异；当前 GUI 不自动运行该功能
- **复杂结构观察**：文本框、脚注尾注、编号重启、合并单元格、落款复杂结构已进入统一上下文、统一门禁和矩阵回归

## 🚫 当前边界

- **项目定位**：当前仍是事务所专用场景程序，不是通用任意模板编辑器
- **不承诺范围**：文本框正文正式接入、脚注尾注正式接入、编号重启正式接入、复杂合并单元格逻辑网格、落款图片锚点正式保护，还在持续补位
- **结果判断方式**：当前以矩阵样本、快照、场景断言和现存真实样本为正式门禁，不声称覆盖已缺失的全部历史真实样例

## 📐 排版规格详细说明

### 🖩 一、封面检测规则

📌 **检测逻辑**：扫描文档前60个元素，如果找到一个表格，且该表格的文本同时包含以下四个关键词，则判定为有封面：
- "会计师事务所"
- "地址"
- "电话"
- "传真"

📌 **纯封面文档判断**：如果按可见有效文本统计不足200个字，判定为纯封面文档，仅处理页边距，不做任何内容排版。

---

### 📝 二、正文段落排版

段落排版是整个工具最复杂的部分，需要按顺序识别出文档中的不同区域，然后分别处理。

#### 🔖 2.1 正文标题区（报告大标题）

📌 **识别规则**：在文档正文的最开头，寻找满足以下条件的段落（最多识别3行）：
- 文字是**加粗**的
- 字号**大于小四**（即大于12磅）

📌 **排版效果**：

| 项目 | 规格 |
|---|---|
| 字体 | 中文宋体 + 英文 Times New Roman |
| 字号 | 三号（16磅） |
| 加粗 | ✅ 是 |
| 行距 | 1.5倍行距 |
| 段前/段后 | 各0.5行 |
| 对齐方式 | 居中 |
| 首行缩进 | 无 |

#### 🔖 2.2 文号行（如"川华信（2024）第123号"）

📌 **识别规则**：在标题区结束后，向后扫描最多5个段落，寻找满足以下条件的行：
- 包含"川华信"且文字长度不超过50字，且不包含"事务所"
- 或者匹配文号格式：川华信 + 年份括号 + 编号 + "号"

📌 **排版效果**：

| 项目 | 规格 |
|---|---|
| 字体 | 中文宋体 + 英文 Times New Roman |
| 字号 | 小四（12磅） |
| 加粗 | ❌ 否 |
| 行距 | 1.5倍行距 |
| 段前/段后 | 各0.25行 |
| 对齐方式 | 右对齐 |
| 首行缩进 | 无 |

#### 🔖 2.3 抬头行（如"XXX公司："）

📌 **识别规则**：在文号行结束后，寻找满足以下条件的行（最多2行）：
- 以中文冒号"："或英文冒号":"结尾
- 文字长度不超过60字
- 包含以下关键词之一：公司、集团、委员会、管理委员会、事务所、研究院、中心、学校、学院、银行
- 但不包含"中国注册会计师"或"四川华信"

📌 **排版效果**：

| 项目 | 规格 |
|---|---|
| 字体 | 中文宋体 + 英文 Times New Roman |
| 字号 | 小四（12磅） |
| 加粗 | ✅ 是 |
| 行距 | 1.5倍行距 |
| 段前/段后 | 无 |
| 对齐方式 | 左对齐 |
| 首行缩进 | 无 |

#### 🔖 2.4 一级标题（如"一、审计意见"）

📌 **识别规则**（按优先级从高到低）：
1. 文字以中文数字+"、"开头，如"一、"、"十二、"（文字长度不超过30字）
2. 文档自带的自动编号格式为"%1、"（可见编号语义）
3. 段落的大纲级别为0（即一级大纲）
4. 段落的样式名称为"Heading1"、"标题1"等

📌 **排版效果**：

| 项目 | 规格 |
|---|---|
| 字体 | 中文宋体 + 英文 Times New Roman |
| 字号 | 小四（12磅） |
| 加粗 | ✅ 是 |
| 行距 | 1.5倍行距 |
| 段前 | 1行（100行距单位 + 240缇） |
| 段后 | 0.5行（50行距单位 + 120缇） |
| 对齐方式 | 两端对齐 |
| 首行缩进 | 无 |
| 大纲级别 | 1级 |
| 与下段同页 | ✅ 是（避免标题孤悬在页底） |
| 自动编号缩进 | 强制清除（目标是修正当前标题的编号呈现；当同一编号模板还被长编号正文共用时，不应连带改坏这些正文） |

#### 🔖 2.5 二级标题（如"（一）管理层责任"）

📌 **识别规则**（按优先级从高到低）：
1. 文字以"（中文数字）"或"(中文数字)"开头（文字长度不超过30字）
2. 文档自带的自动编号必须满足"括号里是汉字数字"这层语义，兼容 `（一）` / `(一)` 以及 `（一）、` / `(一)、` 这两类常见写法；如果编号挂在段落样式上，会先物化到段落自身再做标题清洗
3. 段落的大纲级别为1
4. 段落的样式名称为"Heading2"、"标题2"等

📌 **特别说明**：
- 不是所有括号编号都算二级标题
- `（1）`、`(1)`、`（1）.`、`(1).` 这类"括号里是阿拉伯数字"的内容，不纳入二级标题
- 当前项目没有正式四级标题体系，上述括号数字写法会先按"正文式四级"处理，也就是不再套用二级标题格式

📌 **排版效果**：

| 项目 | 规格 |
|---|---|
| 字体 | 中文宋体 + 英文 Times New Roman |
| 字号 | 小四（12磅） |
| 加粗 | ✅ 是 |
| 行距 | 1.5倍行距 |
| 段前 | 0.5行（50行距单位 + 120缇） |
| 段后 | 0.25行（25行距单位 + 60缇） |
| 对齐方式 | 两端对齐 |
| 首行缩进 | 无 |
| 大纲级别 | 2级 |
| 与下段同页 | ✅ 是 |
| 自动编号缩进 | 强制清除（目标是修正当前标题的编号呈现；当同一编号模板还被长编号正文共用时，不应连带改坏这些正文） |

#### 🔖 2.6 三级标题（如"1．具体内容"）

📌 **识别规则**（按优先级从高到低）：
1. 文字以阿拉伯数字+"、"或"."或"．"开头（文字长度不超过30字）
2. 文档自带的自动编号格式是"阿拉伯数字直接接分隔符"这类语义，例如 `%3、`、`%3.`、`%3．`
3. 段落的大纲级别为2
4. 段落的样式名称为"Heading3"、"标题3"等

📌 **特殊处理**：三级标题的编号分隔符会统一规范为全角点"．"，例如"1."、"1、"都会变成"1．"

📌 **排版效果**：

| 项目 | 规格 |
|---|---|
| 字体 | 中文宋体 + 英文 Times New Roman |
| 字号 | 小四（12磅） |
| 加粗 | ✅ 是 |
| 行距 | 1.5倍行距 |
| 段前 | 0.25行（25行距单位 + 60缇） |
| 段后 | 无 |
| 对齐方式 | 两端对齐 |
| 首行缩进 | 2字符（480缇） |
| 大纲级别 | 3级 |
| 与下段同页 | ✅ 是 |
| 自动编号缩进 | 强制清除（目标是修正当前标题的编号呈现；当同一编号模板还被长编号正文共用时，不应连带改坏这些正文；三级标题自身保留2字符首行缩进） |

#### 🔖 2.7 普通正文段落

📌 **识别规则**：不属于以上任何特殊区域的段落，均为普通正文。

📌 **自动编号正文保留原则**：
- 如果一个正文段落在视觉上仍显示自动编号，但它不属于一级/二级/三级标题，则按“自动编号正文”处理
- 这类段落保留编号，不再因为底层编号来自段落自身、段落样式或其他 Word 机制不同，就被普通正文分支一刀切清掉前缀
- 典型场景包括正文式四级 `（1）/(1)`、普通说明清单、普通编号列表

📌 **排版效果**：

| 项目 | 规格 |
|---|---|
| 字体 | 中文宋体 + 英文 Times New Roman |
| 字号 | 小四（12磅） |
| 加粗 | ❌ 否（强制清除） |
| 行距 | 固定21磅（420缇） |
| 段前/段后 | 无 |
| 对齐方式 | 两端对齐 |
| 首行缩进 | 2字符（480缇） |
| 斜体 | ❌ 否（强制清除） |
| 下划线 | ❌ 否（强制清除） |

📌 **字符级清洗**：正文中的每个文字块都会被清理，移除以下可能存在的格式污染：
- 字符缩放（恢复默认100%）
- 自适应宽度
- 字符间距偏移
- 上下标位置偏移

#### 🔖 2.8 段落排版的安全避让机制

📌 **以下区域的段落不会被段落排版服务触碰**：
- 📊 **表格内的段落**：完全跳过，交给表格排版服务处理
- 🔲 **文本框（`w:txbxContent`）内的段落**：完全跳过，避免侧栏/签章文本框被强套正文格式
- ✍️ **落款区的段落**：完全跳过，交给落款区排版服务处理
- 📜 **封面区域的段落**：如果有封面，段落链会先停留在封面区；但不会再把首节整段一刀切跳过，而是遇到 `目录` 或可识别正文标题后立即退出封面区，开始处理同节里的目录/正文内容

📌 **书签/批注保护**：统一三级标题分隔符等整段替换操作，遇到含书签或批注锚点的段落会跳过，不再静默删除锚点

### 📊 三、表格排版

#### 🔖 3.1 表格识别与过滤

📌 **哪些表格会被处理**：
- 正文区域内的所有表格
- 排版后的表格（已跳过封面区域的表格）

📌 **哪些表格会被跳过**：

| 非首行 + 纯数字 | 右对齐 | 数值列靠右，方便比对；豁免列只保留原显示，不改变对齐判断 |
| 非首行 + 非数字 | 居中 | 文字类内容居中；首列仍按上一条首列规则左对齐 |

#### 🔖 3.5 数值格式化规则

📌 **普通数字的具体范围**：正文表格中，表头区以外、可安全重写、可识别为纯数字且所在列未命中豁免关键词的单元格。表头行一律不参与数值重格式化（“2023”不会被改成“2,023.00”）。

📌 **整列豁免规则**：只要表头包含下列任一关键词，该列所有数据保持原始显示，不添加千分位、不补两位小数，也不清空 `0`：

- 标识类：`序号`、`编号`、`代码`、`号码`、`账号`、`识别号`
- 账户类：表头以`账户`结尾，或包含`账户号`；`账户余额`仍属于金额列，不豁免
- 期间类：`年份`、`年度`、`月份`、`季度`、`日期`、`账龄`、`期数`、`页码`
- 数量类：`数量`、`人数`、`户数`、`件数`、`台数`
- 除上述账户类的专门判断外，其余采用“包含关键词”判断，因此 `项目编号`、`银行账号`、`纳税人识别号`、`报告年度` 等组合表头同样豁免

多行表头会连续识别：Word 已标记为重复表头的行，或首行存在横向/纵向合并时的第二行，均不会按数据行重格式化。列语义以最末层非空表头为准，并兼容 `gridBefore` 和横向合并的逻辑列坐标，避免上层“银行账户”把下层“余额”误判为账号。

📌 **为什么数量列也豁免**：数量在业务上通常是件数、人数、户数、台数等计数，不应被显示成 `1,234.00`；金额、余额、收入、成本、单价等未命中豁免词的数值列，仍按普通数字规则处理。

| 情况 | 处理方式 | 示例 |
|---|---|---|
| 正数 | 千分位 + 两位小数 | 1234567 → 1,234,567.00 |
| 负数（带负号） | 负号 + 千分位 + 两位小数 | -1234 → -1,234.00 |
| 负数（括号表示） | 先转成负号表示，再格式化 | (1234) → -1,234.00 |
| 百分比 | 千分位 + 两位小数 + % | 12.5% → 12.50% |
| 零值 | 单元格清空（不显示0） | 0 → （空） |
| 单独的横杠 | 单元格清空 | - → （空） |

📌 **结构保留原则**：
- 命中纯数字时，优先只改单元格里的文本值，不再粗暴删光整格段落重建；批注等附着结构需要继续保留
- 如果单元格底层结构较复杂，但视觉上看起来仍像数字，程序会先判定“是否可安全重写”；只有安全时才改文本，避免伤到复杂结构

#### 🔖 5.1 落款区定位逻辑

📌 **定位过程**（事务所模板边界定位）：
1. 先扫描全文非空段落，查找事务所落款头部行，例如"四川华信(集团)会计师事务所"
2. 再在其后查找城市签字行，例如"中国·成都"
3. 从城市签字行继续向后查找首个合法落款日期尾行，日期骨架兼容真实日期和模板占位日期，如"2024年12月31日"、"二〇二四年十二月三十一日"、"二〇二六年X月X日"

- 模板边界关键词（事务所落款头部/城市行）为空时直接判定无落款区，避免空串恒真导致的误匹配

- 落款识别看的是用户在 Word 里实际看到的文本，不再只依赖裸 `InnerText` 或单一 `w:t`

📌 **标点兼容**：
- "四川华信(集团)会计师事务所" 与 "四川华信（集团）会计师事务所" 视为同一边界
- "中国·成都" 与对应半角写法视为同一边界

## 🛠️ 技术信息

### 🏆 为什么选择 C# + .NET + OpenXML 而不是 Python + python-docx？

本项目最初使用 Python + python-docx 开发，后来整体迁移到 C# + .NET + OpenXML。这个技术路线选择不是随便做的，而是经过实际踩坑后的理性决策。下面详细说明原因。

#### 🔧 1. 文档操控精度——OpenXML 能做到 python-docx 做不到的事

python-docx 本质上是 OpenXML 的"简化版包装"，它只暴露了最常用的功能，很多底层细节被隐藏了。而排版恰恰需要操控大量底层细节。

📌 **python-docx 无法直接操控的常见场景**：

| 场景 | python-docx | OpenXML（C#） |
|---|---|---|
| 修改自动编号的后缀（编号后的Tab改成无） | ❌ 不支持，需要手动操作XML | ✅ 直接操作 NumberingDefinition |
| 清除段落级 Tab 制表符污染 | ❌ 不暴露这个层级 | ✅ 直接操作 ParagraphProperties |
| 精准控制大纲级别 | ⚠️ 间接支持，不完整 | ✅ 完整支持所有14级大纲 |
| 表格单元格私有边框覆盖 | ❌ python-docx的表格边框API很粗糙 | ✅ 精确到每个单元格的每条边 |
| 页眉页脚的分节管理 | ❌ 非常痛苦，几乎不可用 | ✅ 按 SectionProperties 精确控制 |
| 自动编号格式的完整读取 | ❌ 只能拿到编号结果文本 | ✅ 能读取完整的 NumberingFormat 定义 |
| 字符级格式清洗（缩放/间距/上下标） | ⚠️ 部分支持，经常遗漏 | ✅ 每个属性都能精准读写 |

> 💡 简单来说：python-docx 是"傻瓜相机"，拍日常照片够用，但要做精细的后期修图就力不从心了。OpenXML 是"单反相机"，所有参数都能手动调节。

#### ⚡ 2. 性能——批量处理时的速度差距

| 对比项 | Python + python-docx | C# + OpenXML |
|---|---|---|
| 单文件处理速度 | 基准 | 快 3-5 倍 |
| 批量100个文件 | 较慢 | 显著更快 |
| 内存占用 | 较高（Python的GC机制） | 更低（.NET的优化GC） |
| 启动时间 | 需要启动Python解释器 | 原生执行，启动即跑 |

> 💡 C# 是编译型语言，直接跑机器码；Python 是解释型语言，每行代码都要翻译一遍。处理几十上百个 Word 文档时，这个差距会非常明显。

#### 🎨 3. 界面能力——WPF vs Tkinter/PyQt

| 对比项 | Python（Tkinter/PyQt） | C# WPF + WPF-UI |
|---|---|---|
| 原生 Windows 风格 | ❌ Tkinter很丑，PyQt勉强 | ✅ Win11 Fluent Design 原生体验 |
| Mica 毛玻璃背景 | ❌ 不支持 | ✅ 系统级支持 |
| 深色主题 | ⚠️ 需要第三方库，效果一般 | ✅ 系统级支持，一键切换 |
| 动画和过渡效果 | ⚠️ 需要大量手写 | ✅ XAML声明式动画 |
| 控件丰富度 | 一般 | 非常丰富 |
| 和 Windows 的集成度 | 低 | 原生，深度集成 |

> 💡 用户体验不是可有可无的装饰。一个好看的界面能让用户（特别是非技术人员）更愿意使用工具，减少抵触感。

#### 🔒 4. 类型安全——编译时就能发现问题

Python 是动态类型语言，很多错误要等到运行时才会暴露（比如拼写错误、参数类型不对、属性不存在）。

C# 是静态类型语言，**写代码的时候就能发现大部分错误**：
- 拼错了属性名？编辑器立刻红色波浪线提示
- 参数类型传错了？编译都过不了
- 空值没有处理？编译器会警告

> 💡 这意味着：用C#写的排版工具，不太可能出现"处理到一半突然崩溃"的情况。而Python脚本在处理某些特殊格式的文档时，可能会因为意外的情况而报错中断。

#### 🏗️ 5. 代码可维护性

| 对比项 | Python | C# |
|---|---|---|
| 大型项目组织 | ⚠️ 超过10个文件就开始乱 | ✅ 命名空间、项目结构清晰 |
| 接口和契约 | ⚠️ 靠自觉 | ✅ 强制接口定义 |
| 重构安全性 | ❌ 改一个函数名可能牵连一堆地方 | ✅ 编辑器自动帮你改所有引用 |
| 单元测试 | ✅ 有pytest | ✅ 有内置测试框架 |
| 调试体验 | 一般 | ✅ Visual Studio调试器非常强大 |

> 💡 当工具越来越复杂（比如加入了封面检测、落款区识别、安全避让机制等），C# 的强类型和严格结构能让代码始终井井有条，不会越改越乱。

| 维度 | Python + python-docx | C# + OpenXML | 胜出 |
|---|---|---|---|
| 文档操控精度 | ⭐⭐ | ⭐⭐⭐⭐⭐ | 🏆 C# |
| 处理性能 | ⭐⭐ | ⭐⭐⭐⭐⭐ | 🏆 C# |
